The Buddy Mailroom

How the thing we built works, explained the way you'd explain it to a curious ten-year-old. Every part has a picture, a plain story, and a small blue box with the grown-up words so an engineer can find it in the code.

1The big idea: a mailroom for every shop

Imagine a shop. All day, little letters arrive about things that happened: "Priya put a kurti in her cart", "Rohan paid for his order", "the WhatsApp message was read". Our system is a mailroom. It keeps every letter, works out who each letter is about, follows the shop's rulebook to decide what to say next, asks a gatekeeper whether it's allowed to say it, and then a postman sends the message. That's it. Everything else is detail.

Letters come in through doors, sit in one tray, get read with a dictionary, matched to a person, checked against the rulebook, stopped at the gate if needed, and only then sent.

Grown-up words. The mailroom is app/crm in clairvoyance. Doors and tray = record (the event spine, table T13). Reader and dictionary = the decode engine and the catalog (T24). Address book = identity. Rulebook and tokens = outreach (workflows, runs). Gate = permission. Postman = connectivity (the manifest T16, one send path). One sentence rules them all: edges translate, the spine records, bridges call contracts, contracts write.

2The doors: how letters get in

There are three doors. The front door is where a shop's own computer pushes letters ("an order was placed"). The side bays are where WhatsApp rings the bell with its own letters ("delivered", "she replied"). The little office door is where a new company tells us what their letters will look like before they send any. Every door follows the same four steps, always in this order: check the ID, stamp the envelope, put it in the tray, say "got it". The door never opens the letter to read it. Reading is someone else's job.

Three doors, one habit. Store first, understand later.

  • If the ID is wrong, the door says no and nothing is stored.
  • If the same letter arrives twice, the second one is quietly dropped, but we still say "got it" so the sender doesn't keep knocking.
  • A door in any other part of the building is not allowed. One mailroom, one set of doors.
Grown-up words. POST /ingest/events (front door, s2s token), GET|POST /ingest/webhooks/{provider} (the provider bays, dispatched through record's INGRESS registry, Meta's entry registered at the composition root), POST /ingest/schemas (vendor registration into T24). Verify, stamp the envelope, INSERT ... ON CONFLICT DO NOTHING on (merchant, source, external_id), 200. Parsing before storing is a BLOCKER (ADR 0020). A body over 1 MiB is refused while streaming.

3The tray: every letter is kept, in order

All letters land in one tray, oldest first. Nobody ever throws a letter away. A worker takes a small pile from the top, deals with each letter, and stamps it "done". If a letter can't be understood (say, it has no phone number and no name at all), it goes to the "look again" shelf. It stays there, safe, until someone teaches the reader how to read that kind of letter. Then it's read again as if it just arrived.

Stored raw, immutable, replayable. The worker's pile is small so a bad letter costs one letter, not the whole day.

Grown-up words. crm_event_raw is partitioned by month and immutable by trigger; only processed_at, quarantine_reason, customer_id and attempts may change. The worker claims a batch with FOR UPDATE SKIP LOCKED, one savepoint per row, five attempts then quarantine. replay() resets a row. Consumers never dedupe; the tray already did.

4The reader and the dictionary

Letters come in many languages. A Shopify letter and a WhatsApp letter and a ride-app letter all say "who" and "what" in different places. So we have one reader and a dictionary for every kind of letter. The dictionary says: "in a Shopify order letter, the phone is here, the name is there, the total is there." For our own connectors, we write the dictionary page (and we test it against real letters we recorded). For a new company, they write their page when they sign up. Same reader, same rules. Nobody ever types a field name from memory again. If it's not in the dictionary, you can't filter on it, and so you can't misspell it.

One reader, two kinds of dictionary pages. The editor, the filters and the message fill-ins all read from the same pages.

Grown-up words. extractors/engine.py executes a DecodeSpec built from either a code CatalogEntry (extractors/shopify.py, extractors/whatsapp.py, assembled via SPEC_MODULES) or a registered T24 row (cached 60s; the table stays cold). Identity roles in precedence order, fallbacks, derive() for the 10% that is logic, about for letters that name no person. Fixtures double as conformance tests: every declared field must appear in a recorded payload. The publish validator only accepts declared fields; ops are a function of type.

5The address book: who is this letter about?

Every letter is about a person, and the address book finds them. It looks for a phone number first, then an email, then a few other ids. It never guesses ("Priya S. is probably Priya Sharma"? No. Never.). If nobody matches, a new card is made. Sometimes we discover two cards are the same person, because a letter carries both her old phone and her new email. Then we staple the cards together. We never melt them into one, and we never throw one away, so we can always un-staple if we were wrong.

A website visitor who hasn't logged in yet gets a card too, with just a sticker number from a cookie. The day she types her phone at checkout, her sticker card and her phone card get stapled. Nothing special has to happen. A letter carrying both is enough.

Deterministic, one creator, staple never melt. The sticker card is how tracking-before-login fits without a new rule.

Grown-up words. resolve(merchant, handles) is the only creator of crm_customer rows; probe order phone, email, igsid, shopify_customer_id, external_ref against partial unique indexes; no fuzzy matching (ADR 0017). Merge = status flip + merged_into_id, path-compressed to one hop; a handle owned by another row is staple evidence, survivor is the older card. Facts carry an evidence ladder (declared, observed, imported, inferred; ADR 0021). The visitor card is a proposed merchant-scoped anon_id handle column, the igsid precedent; a ruling owed.

6The rulebook and the board game

The shop writes rules like a recipe: "When a checkout is left and the payment is cash-on-delivery, wait 15 minutes, send a WhatsApp, if she doesn't reply in an hour, call her." A rule is a little board with squares. When a letter matches the rule, a token is placed on the first square for that person, and a walker moves it square by square. If she pays in the middle, her token is taken off. Once a token starts on a board, it finishes on that version of the board, even if the shop edits the rule tomorrow. The shop can only choose words from the dictionary when writing a rule, so a rule can't quietly wait for a field that doesn't exist.

Doors, squares, tokens, goals. Editing a live board never strands a token mid-game.

Grown-up words. Workflows (T19) with a typed entry.where, versions (T25, ADR 0023: a run executes the version it entered under, on_publish: pin | migrate), enrollments (T20) walked on leases with compare-and-set writes, goal tiers, repeat policies, ladders. Node vocabulary wait · send · call · wait_event in the NODE_TYPES registry. Publish gathers the catalog then validates purely; send nodes map template blanks to declared variables explicitly.

7The gate: may we talk to her?

Before the postman sends anything, the gatekeeper asks four questions. Did she say it's okay to hear from this shop? Is it a polite hour? Have we already messaged her a lot this week? Is this the right kind of message for what she agreed to? If the answer to any question is no, the message doesn't go. And here is the strict part: if the gatekeeper isn't sure, because a lamp went out or a list can't be read, the answer is NO. Being unsure is never a yes. Every answer, yes or no, is written in the logbook so the shop can see why a message did or didn't go.

Fail closed. No override button exists anywhere in the building.

Grown-up words. may_contact() (ADR 0018): consent ledger + resolved state written in one transaction, quiet hours, frequency caps, purpose; every verdict writes a decision_log row; a gate verdict is never cached; no bypass flag, ever. Suppression on platform_identity is global across shops. Today's sends are gated by suppression; the full may_contact() is the open PR #1021.

8The postman: one way out

There is exactly one way a message leaves the building: the postman's bag. Not a side window, not a friend's pocket. Before a message goes in the bag, it gets a ticket that is good for one message only. WhatsApp only accepts approved letter templates, so the shop registers its templates first and we remember which ones are approved. After the postman delivers, WhatsApp sends little ticks back ("sent", "delivered", "read"), and those come in through the side bay as letters like any other, so the whole story is in the tray.

One send path, one manifest, single-use tokens, approved templates, receipts as letters.

Grown-up words. send(send_token, message_id) is the only provider call (ADR 0015); tokens are Redis GETDEL, 60s. crm_message (T16) is the single delivery authority, nine status words in status.py. Templates live in T23 with a publish-time check on the account the route will send from. Providers are adapters behind the CONNECTORS registry; the WhatsApp adapter renders positional or named parameters, one style per template.

9The window: what the shop sees

The shop looks through a window at the mailroom. It sees each customer's story (every letter about her, in order), the boards and how many tokens are on them, which templates are approved, and, importantly, why a message didn't go, in plain words from the gatekeeper's logbook. The window only shows words from the dictionary, so what you can pick is exactly what the reader can read.

Journey, flows with seen-versus-matched, templates, and the logbook's reasons.

Grown-up words. The loom console over /customers, /workflows, /connectors, /catalog; no category word on any external path (ADR 0022). The flows editor is next in the U-lane and renders its pickers from GET /catalog.

10How big can the mailroom get?

Today it's a small, tidy room: about one letter a second arrives, and it could handle thirty a second all day without sweating. To grow, you don't redesign the room. You add more workers at the tray, then a bigger tray split into monthly drawers, then a second reading room for looking things up. Only when letters arrive faster than five thousand a second, every second, for hours, do you change how letters travel: a conveyor belt replaces the tray as the queue, and the tray becomes the archive. Everything after the reader stays exactly the same.

Three sizes of the same room. Each step has a named trigger; nobody builds the belt before the tray is full.

Grown-up words. Estimates from the code, not measurements: the door is one local JWT check and one insert (~1–3 ms); the pass is 6–12 round trips per letter, sequential per replica (40–100/s each). SKIP LOCKED makes replicas near-linear until the connection budget. Past ~5k/s sustained, Postgres-as-queue ends: Kafka/Redpanda in front, crm_event_raw becomes a sink, identity sharded by merchant. A 15-minute load test over the recorded Shopify fixtures is the named step that replaces estimates with numbers.

11Many shops, clicks from browsers, letters from servers

One mailroom serves many shops at once. Every envelope has the shop's name on it, and there are walls between shops: a letter for the kurti shop can never be read by the shoe shop, and a person who said "stop" to one shop is not bothered by that shop again. There are also two kinds of senders. A shop's server sends important letters: an order, a payment, a cancellation. A shopper's browser sends tiny notes: "looked at a product", "scrolled", "added to cart". Browsers send forty notes a visit. If every note went into the tray, the tray would overflow in an afternoon. So tiny notes go into a notebook next door, cheap and huge, and a helper reads the notebook and writes one real letter when something meaningful happened: "she looked at the blue kurti three times and left". That letter goes in the tray, and the rulebook treats it like any other.

Server letters go to the tray; browser notes go to the notebook; the helper turns notes into moments. Walls between shops always.

  • Every table has the shop's name as its first key. A query without it is a bug, not a style issue.
  • Shopify gives us the visitor sticker for free through its pixel. Other stores get a small snippet, or Jitsu as the collector.
  • Segments ("everyone who spent over 5k this month") are a question for the notebook and the tray together; "she just crossed 5k" is a letter from the helper. Two questions, two homes.
Grown-up words. Tenancy: merchant_id first in every unique index; suppression global on platform_identity, consent per shop. Client events: a collector (Jitsu or ours), a columnar sink (a partitioned Postgres table for the first store, ClickHouse at ~50M/day), a derive job emitting moments as letters keyed by anon_id. Rollups (monthly spend) are the same pattern: sum on hearing, never a stored counter, one derived letter with a deterministic external id. Vendors register their schema at POST /ingest/schemas and need no code from us.

12Is Python the right fit, and is it built properly?

Short answer: yes, and mostly. The mailroom's work is waiting: waiting for the database, waiting for WhatsApp to answer. It is almost never hard arithmetic. Python with async is good at waiting on many things at once, and it is the language the rest of the company's system already speaks, so the mailroom can share the building. When the mailroom is slow, it is because of how many trips it makes to the database, not because of the language. Rewriting in a faster language would make the same trips at the same speed. The belt, when it comes, changes the trips, not the language.

I/O-bound work in an async language, with the rules enforced by machines, not by memory.

The laws are real, not slogans. Store first, one send path, fail-closed gate, one creator of customer cards, staple never melt, no vocabulary in database checks. Each one has a test or a trigger that fails when it is broken.
The shape holds under growth. Registries instead of if-chains for extractors, node types, connectors, ingress, the catalog. A new channel or vendor is one file and one line, and the CI square proves it.
Boundaries are enforced by a script. Only the owning module may write its tables; contracts are the only cross-module door; the composition root fills the slots so nothing imports in a circle.
Capacity is estimated, not measured. The numbers above come from reading the code. One load test replaces them. PgBouncer, the one infrastructure item, is still owed.
The full gate is still a pull request. Sends are gated by the global stop-list today; consent, quiet hours and caps arrive with #1021. Nothing sends a marketing message to strangers until then, by design, but the pilot needs it.
The window lags the mailroom. Customers and templates are on screen; the flows editor is designed and not yet built. Until it is, boards are written as files.
Three rulings are open. Whether a board names its letter's source as well as its topic; whether the manifest stores the provider's error code or a readable word; whether delivery receipts are attributed to the customer.
Grown-up words. FastAPI + asyncpg + Postgres, one image and a CRM_ROLE per pod (event-worker, dispatcher, walker). Pure decide functions between gather and apply, accessors declared by signature, queries return (sql, params). Gates: black, isort, autoflake, pyrefly, migration numbering against the live base, migrations never edited, boundary checker, tests, one commit. The corpus at buddy-cpaas-docs is the source of truth and every merged PR is integrated back into it the same day.
