Where it's been

A run knows which square it stands on and nothing else. The square it just left, the branch it picked, how long it waited, how many times it failed on the way — all of it is overwritten by the statement that moves the token. Here is exactly what is lost, what already survives, and the one table that fixes it without touching the hot path.

02

Five things the row forgets, and how

These are five different mechanisms, not one missing feature. Three of them are deliberate and correct; they just have no counterpart anywhere that remembers.

Release c1eca642
LostWhereThe mechanism
The square it left queries/enrollment.py:231 SET current_node = $2. One row, updated in place. After it commits the previous value exists nowhere.
Squares walked mid‑chain walker.py:181–241 The visit loop only writes when the next square is a wait. A send → condition → split → send chain is one UPDATE.
The branch it picked walker.py:210–214 without_reply(context, node.id) runs before the write. Correct — a door may restart a run on a square it has already visited, and a stale reply would resolve the revisit instantly — but the answer never reaches disk.
When it arrived canon T20 col 9 entered_at is the run's birth. wake_at is the next alarm, and the claim pushes it forward every lease, so it is not a stamp of anything. There is no arrival column.
Retries and holds queries/enrollment.py:236 attempts = 0, last_error = NULL on every successful step. A run that failed four times and then moved looks pristine. And a windowed hold calls advance_run with its own node id — byte-identical to a step.
The consequence, in the merchant's words

“Why did this customer get the discount version?” — unanswerable for a condition. “How long has she been sitting there?” — no column holds it. “Did this run retry before it went through?” — erased by the step that succeeded.

03

What already survives — don't rebuild it

Outreach has been growing a history by accident, in the wrong place. Four of the five bookkeeping prefixes in a run's context are per-square records. They have no times, no order, and they sit inside the walker's own working state.

SquareRecoverable todayHow
send yes — with time, delivery and gate verdict T16 source_kind='workflow', source_id = run.id, and dedupe_key = '<run>:<node>' — the node id is in there, as a string nobody queries as a key
call yes — with time lead_call_tracker.meta_data.enrollment_id, plus a uuid5 minted per visit
action outcome only action_<node> in context. No time, no order
split arm only split_<node> in context. No time, no order
condition nothing The answer is cleared on the way out and never written
wait nothing No arrival, no duration, no record that a letter cut it short
order, timing, retries, holds nothing —
The codebase already knows the answer

split.execute returns its answer twice — once as reply_<node> for the walker, once as split_<node> as a durable fact. Its docstring says why: “the reply is cleared when the token leaves the square, and a report that groups runs by arm has to read it days later.”

The right instinct is already in the file. It was applied to one of the two branching squares, without a time, in the one jsonb blob that must stay small. T26 is that instinct, finished.

04

Two shapes to refuse before starting

refused

A history array on T20

That row is the only stateful row in outreach and the walker compare-and-swaps on it every visit. Appending means rewriting the whole array under the lease, on the hottest row in the module, forever.

It is the photocopy habit canon already refuses for context.

refused

Steps as letters on the spine

A walker step is not something that happened in the customer's world — it is our machinery. On T13 it becomes a topic a door could listen for, a payload the decode engine would try to walk, and a row the retention model treats like a checkout.

Keep the spine for letters.

The precedent that does fit

Canon already has exactly this table for exactly this reason. crm.decision_log (T14) is “the one genuinely unreconstructable table: the accountability bill the inversion runs up, paid in rows.” The gate keeps a decision log. The walker keeps none. T26 is the walker's.

05

The table

One row per completed step, inserted and never edited. The square the run stands on right now is not in here — it is on the run row, where it already was. That is what removes the update path entirely.

073_create_crm_workflow_step.sqlcanon T26
-- 073: crm_workflow_step (canon T26) — where a run has BEEN.
-- The token's position stays on T20; this is the trail behind it.
-- Append-only: rows are inserted by the statement that moves the
-- token and are never updated. The walker NEVER reads this table.

CREATE TABLE crm_workflow_step (
    id               bigserial    PRIMARY KEY,
    merchant_id      text         NOT NULL,
    enrollment_id    uuid         NOT NULL,
    workflow_id      uuid         NOT NULL,
    workflow_version integer      NOT NULL,   -- a migrate re-pins mid-run
    node             text         NOT NULL,
    node_type        text         NOT NULL,   -- render 40 steps without resolving 40 documents
    arrived_at       timestamptz  NOT NULL,
    left_at          timestamptz  NOT NULL,   -- only closed steps are written
    arrived_by       text         NOT NULL,   -- door | timer | letter | walk
    outcome          text,                    -- the edge label, timeout, else, the arm; NULL = plain square
    next_node        text,                    -- NULL = the run ended here
    attempts         smallint     NOT NULL DEFAULT 1,
    last_error       text,
    CONSTRAINT crm_workflow_step_run_fk
        FOREIGN KEY (enrollment_id)
        REFERENCES crm_workflow_enrollment (id) ON DELETE CASCADE,
    CHECK (left_at >= arrived_at)
);

-- The per-run read, AND the index the cascade delete needs: a FK
-- column must LEAD its own index or the retention sweep seq-scans
-- this table once per run it removes.
CREATE INDEX crm_workflow_step_run_ix
    ON crm_workflow_step (enrollment_id, arrived_at);

-- The per-square funnel: "how many runs reached this square, and
-- where did they go from it" — merchant-first, tenancy law.
CREATE INDEX crm_workflow_step_node_ix
    ON crm_workflow_step (merchant_id, workflow_id, node, left_at);
T20 gains one columncol 19
-- The batch has to know where it started. This is the only change
-- to the run row, and the only place the current square's arrival
-- time lives until the step closes.

ALTER TABLE crm_workflow_enrollment
    ADD COLUMN node_arrived_at timestamptz;   -- NULL for runs that pre-date 073
Three laws that keep it from rotting

The walker never reads it. current_node stays authoritative for execution; T26 is the record, exactly as decision_log is never read by the decider. The day something on the hot path reads it, the design is wrong — and it is what keeps the table droppable and partitionable without touching execution.

Rows are never edited. No open row, no partial unique, nothing to reconcile against current_node.

Every read is a union. The past is N closed rows; the present is the run row plus node_arrived_at. That union is a function in outreach/, and any consumer that forgets it shows a timeline one square short of the truth.

06

The flush — one statement, one round trip

The walker buffers finished squares in memory as it walks. When the token stops, the whole batch rides into the database attached to the CAS that moves the run. Ten squares cost one extra statement, not ten.

advance_run_querythe lease is still the generation
WITH moved AS (
    UPDATE crm_workflow_enrollment
       SET current_node    = $2,
           wake_at         = $3,
           context         = $4::jsonb,
           node_arrived_at = $5,          -- when the token lands on the NEW square
           attempts        = 0,
           last_error      = NULL
     WHERE id = $1
       AND status  = 'waiting'
       AND wake_at = $6                   -- THE LEASE. a stale one matches nothing
 RETURNING id, merchant_id, workflow_id, workflow_version
), wrote AS (
    INSERT INTO crm_workflow_step
           (merchant_id, enrollment_id, workflow_id, workflow_version,
            node, node_type, arrived_at, left_at, arrived_by,
            outcome, next_node, attempts, last_error)
    SELECT m.merchant_id, m.id, m.workflow_id, m.workflow_version,
           s.node, s.node_type, s.arrived_at, s.left_at, s.arrived_by,
           s.outcome, s.next_node, s.attempts, s.last_error
      FROM moved m, jsonb_to_recordset($7::jsonb) AS s (
               node text, node_type text,
               arrived_at timestamptz, left_at timestamptz,
               arrived_by text, outcome text, next_node text,
               attempts smallint, last_error text)
 RETURNING 1
)
SELECT (SELECT id FROM moved) AS moved_id,
       (SELECT count(*) FROM wrote) AS steps;

moved is empty when the lease is stale — a reply or a repeat landed mid-visit and moved wake_at. The join then produces no rows and the history is discarded with the move it belonged to. A step row exists if and only if the move committed. No dual write, no drift, nothing to reconcile, no reaper.

Where the numbers come from

attempts and last_error ride in the buffered payload, read off the run before the reset in the same statement — the walker already holds both from its claim. attempts is only ever zeroed by this UPDATE, so the number on a flushed row is exactly “how many claims this square cost.”

What the manifest already guarantees

A send commits on its own connection, before the advance. If the visit dies in between, the message exists and the step does not — and the retry's dedupe_key absorbs the duplicate send, then flushes the step. So T26 records commits and the manifest records attempts, which is a clean seam and not an accident.

One known imprecision, stated rather than hidden

A migrate publish can re-pin an open run between its arrival and its departure, so a flushed row names the version in force when the step closed, not when the token landed. Node ids are minted once and never regenerated, and migrate refuses to delete an occupied node, so rendering is safe either way. Recording the arrival version too would mean a second column on the hot row for a rare case; not worth it, but it belongs in the column's canon note.

08

Three traps

Each of these produces a plausible-looking timeline that is wrong, which is worse than no timeline. All three are cheap to prevent and expensive to discover.

trap 1

The hold restamps the arrival

A windowed square calls advance_run with its own node id (walker.py:191–203). Key the flush on “we called advance” and every overnight hold writes a zero-length step and resets the clock.

Rule: flush and restamp only when next_id != current_id. “Waiting since Friday” must not render as “waiting since 9am”.

trap 2

Resume erases the park

resume_run_query sets attempts = 0; the letter path (resume_run_by_id_query) sets attempts = 0, last_error = NULL for a parked run. Both fire before any step row exists.

So a run that parked, sat visible for a day and was resumed flushes a row claiming one clean attempt. Either the resume paths flush their own row, or a park is only visible while it is happening. Rule it; don't discover it.

trap 3

The goal ends runs without the walker

cancel_run_query is the event side: unconditional, fires when the goal event lands, exits the run wherever it stands. No claim, no visit, no flush.

Every converted run — the ones that matter most — would lose its final square. This is the site that gets missed.

09

Rulings owed, and the order to build in

Does a hold get its own row?

The run has not left the square, so strictly no — stamp held_until instead. But “we held her overnight for calling hours” is exactly what a merchant asks about, and it may deserve to be visible as its own line.

Does a step carry the letter that cut it short?

A cut_short_by uuid into crm_event_raw is a pointer, not a photocopy, and it is the deep link the timeline wants. Recommended: take it.

Backfill, or honest nulls?

Open runs have no arrival stamp. NULL is honest. Defaulting to entered_at is a lie for a run that has been walking nine days — and it is the kind of lie that ends up in a merchant-facing “waiting since”.

Retention: cascade now, partition later?

sweep_exited_runs_query deletes runs in batches; the cascade removes their steps for free. RANGE partitioning on arrived_at is the stage-2 move — written down now, built when volume asks, the way scaling-stages handles everything else.
